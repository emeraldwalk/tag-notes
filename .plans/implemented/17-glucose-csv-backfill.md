## Implementation notes (2026-11-25)

- **One reading per ts, not per (ts, kind).** Plan 14's key is `(user_id, source, ts)`, with no `kind`, and 287 scans
  in the export fall on the same minute as a historic reading. The parser keeps the historic reading and counts the
  scan as skipped, rather than rebuilding the live table to add `kind` to the key. The owner's file gives 98,883
  historic and 1,118 scans (288 skipped, 1,639 ignored), from 2025-11-19T00:45Z to 2026-11-26T02:33Z.
- **Fall back** is as expected: 12 pairs, assigned earlier/later in file order, so 06:00–07:55Z on 2026-11-01 zigzags
  (e.g. 231, 203, 222). Looking at the values, the right split is clear from continuity (one hour flat around 230,
  the other falling from 224 to 197). A small two-state best-fit over each pair could fix it if reports ever care.
- Parsing the whole file takes about 0.75 s in Node; the UI shows "Reading…" meanwhile.
- `POST /api/ingest/glucose` now checks `OWNER_USER_ID` (503) before reading the body, and uses `body.ts`'s
  `readJson`; its tests pass unchanged.
- The UI is `pwa/src/components/GlucoseImport.tsx`, inside `GlucoseSection`.

## The export (from the owner's file, `data/glucose_11-25-2026.csv`, 2026-11-25)

From libreview.com → Download Glucose Data. About 6 MB with 101,930 lines, CRLF line endings, no quoted fields.

- **Line 1** is metadata: `Glucose Data,Generated on,11-26-2026 02:52 AM UTC,Generated by,<name>`.
- **Line 2** has the headers: `Device,Serial Number,Device Timestamp,Record Type,Historic Glucose mg/dL,Scan Glucose
  mg/dL,Non-numeric Rapid-Acting Insulin,Rapid-Acting Insulin (units),Non-numeric Food,Carbohydrates (grams),…,Notes,
  Strip Glucose mg/dL,Ketone mmol/L,…` (21 columns).
- **Device Timestamp** is `MM-DD-YYYY hh:mm AM|PM`, zero-padded, with no seconds and no zone. It is the phone's
  **local** time.
- **Record Type** counts: `0` historic 98,883 (every 5 minutes, Libre 3), `1` scan 1,406, `4` long-acting insulin 2,
  `5` food 8, `6` events with no values 1,629. The file isn't in time order across serial numbers (two serials, one
  with only 3 type-6 rows).
- **DST:** spring forward (2026-03-08) is clean: 01:57 is followed by 03:02. On fall back (2026-11-01) the 01:00–01:55
  readings appear **twice each, as adjacent pairs**, and which one of a pair is the earlier hour can't be told from
  the file (the values don't line up consistently).
- No `HI`/`LO` or other non-numeric glucose values in this file, but other exports may have them.

## Contracts

### Parser — `pwa/src/lib/glucose/csv.ts` (new)

```ts
export type CsvReadingKind = 'historic' | 'scan';

export interface CsvReading {
  ts: string;            // UTC, ISO 8601 with Z, to the second (as plan 14's `ts`)
  mgDl: number;          // integer
  kind: CsvReadingKind;
}

export interface ParsedGlucoseCsv {
  readings: CsvReading[];   // sorted by ts, one per ts
  historic: number;         // count of readings by kind
  scans: number;
  skipped: number;          // rows of type 0/1 that weren't usable (bad value, a time that doesn't exist locally, a duplicate)
  ignored: number;          // rows of other record types (insulin, food, events)
  first: string | null;     // earliest / latest ts
  last: string | null;
}

export class InvalidGlucoseCsvError extends Error {}

export function parseLibreViewCsv(text: string, timeZone: string): ParsedGlucoseCsv;
```

- Strip a BOM and handle `\r\n` or `\n`. Line 1 must start with `Glucose Data`. Columns are found **by header name**
  on line 2 (`Device Timestamp`, `Record Type`, `Historic Glucose mg/dL`, `Scan Glucose mg/dL`), not by position.
  If one is missing, throw `InvalidGlucoseCsvError` with a message the UI can show. An mmol/L export (its headers end
  `mmol/L`) gets its own message: export in mg/dL.
- A timestamp that doesn't match `MM-DD-YYYY hh:mm AM|PM` throws (other regions' formats are rejected, not guessed).
- Type `0` → `historic` from the Historic column, `1` → `scan` from the Scan column. A value that isn't an integer
  from 20 to 600 is `skipped`. All other types are `ignored`.
- **Local → UTC** in `timeZone` (an IANA name) with `Intl.DateTimeFormat`, not `new Date(string)`. A local time that
  doesn't exist (spring forward) is `skipped`. For an ambiguous time (fall back), the *n*th row with the same local
  time and kind (in file order) gets the *n*th of the possible instants, earliest first. The order within that hour
  is a guess (see the export notes): at most one hour a year, accepted.
- One reading per ts (see the implementation notes): a historic reading wins over a scan at the same minute; other
  duplicates are kept once. Both count as `skipped`.
- Pure function, no DOM. 100k rows should parse in well under a second on the phone.

### Route — `POST /api/glucose/import` (signed in)

Mounted in `glucoseApi` (`worker/src/glucoseRoutes.ts`), so the session middleware has run. Rows go under
`c.var.session.sub`, not `OWNER_USER_ID`.

```json
{ "readings": [ { "ts": "2025-11-19T00:45:00Z", "mgDl": 187, "kind": "historic" } ] }
```

- `readings` 1…500 (`MAX_INGEST_READINGS`); `ts`, `mgDl` and the future check as `POST /api/ingest/glucose`;
  `kind` `"historic"` | `"scan"`. Stored with `source 'csv'`, `trend` null, through `insertReadings`.
- → `200 { "inserted": n, "duplicates": m }`; `400 {"error":"invalid","detail":"…"}`; `415`; `413` over 256 KB;
  `401` signed out.
- Factor the per-reading checks out of the ingest handler into a shared function, so both routes use one set of rules.
  The ingest route's behaviour doesn't change.

CPU: each request is up to 36 `INSERT`s of 14 rows in one `db.batch`. Measure with `wrangler tail`. If a request
gets near 10 ms, lower the PWA's chunk size; the route's limit stays at 500.

### PWA — Settings → Glucose (`pwa/src/components/GlucoseSection.tsx`)

- An **Import LibreView CSV…** button (file input, `.csv`). Read the file with `File.text()` and parse it with the
  browser's zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`).
- Preview before sending: the counts by kind, skipped and ignored, the first and last dates, and the time zone used.
  Then **Import** / **Cancel**.
- Send chunks of 500 one at a time, showing `n of N`. Sum `inserted` and `duplicates`, and show them at the end.
  Stop on the first error and say so. Re-importing is safe (the primary key is `user_id, source, ts`), so the
  message says to import the same file again to finish.
- An API helper in `pwa/src/lib/account.ts` next to `getGlucoseStatus`:
  `importGlucose(readings: CsvReading[]): Promise<{ inserted: number; duplicates: number }>`.

## Concept boundaries

- **`/api/import`** (plan 6/8) imports the app's own export file. **`/api/glucose/import`** is this plan's CSV
  readings. Keep them separate, and keep the Settings UI for them separate (Backup vs Glucose).
- **`source 'csv'`** overlaps `'llu'` from 2026-11-24 onward. Both are stored. Plan 14 already says reads return
  both and reports decide. Don't drop CSV rows that LLU also has: CSV fills LLU's gaps (e.g. the first 2 hours).
- **`kind`**: CSV type 0 is `'historic'` (like LLU's graph points, but every 5 minutes, not 15). Type 1 is `'scan'`.
  The CSV never produces `'current'`.
- Insulin (type 4) and food (type 5) records are out of scope. Medicine and food have their own logs (plans 16, food).

  `Glucose Data` and a bad timestamp format each throw `InvalidGlucoseCsvError`.
